# メモリ管理規約

**案件を問わず、メモリの集まりが満たすべき条件。**全プロジェクトへ自動ロードされる。
保管庫のルートは `C:\Users\nr202\iCloudDrive\iCloud~md~obsidian\`。以下 `<保管庫>` と書く。

> **他のルールとの分担** — 各ストリームの `AIメモリ/*.md` はその案件**固有**の手順を持つ。
> **このファイル**は全ストリームに共通する**運用**を持ち、固有の手順をここに書かない。
> 記述が衝突したらこのファイルを正とし、**固有側を直す。**両論併記にしない。

**点検の実務（検査項目・自律の範囲・安全弁）は11節が指す `reference/点検項目.md` が持つ。**
このファイルには基準だけを置き、適用のしかたを書かない。

## 1. メモリセットの最小構成

**1案件 = 1ストリーム。** ストリームは以下の4役を必ず持つ。欠けたら不健全。

| 役 | 置き場 | 責務 |
|---|---|---|
| **索引** | 保管庫に1本（`<保管庫>\personal\AIメモリ\MEMORY.md`） | 全ファイルへのポインタ。**1ファイル1行** |
| **規約／設計** | `<ストリーム>/AIメモリ/` | この案件の進め方。**手順の唯一の正** |
| **本体** | ストリーム直下 | 成果物。読まれるもの。**人間からの明確な指示がない限り自動編集不可** |
| **作業ログ** | `<ストリーム>/AIメモリ/作業ログ.md` | 古い記述を削除して常に最新の情報で管理する |

- 索引はストリームごとに作らない。**保管庫全体で1本。**
- 規約が2本以上に分かれるときは番号を振り、**同じことを2か所に書かない**

## 2. 更新は置換。追記しない

**古い記述は削除して、新しい記述で置き換える。**

- 「以前は〜だったが今は〜」と書かない。現在の事実だけを書く
- 内容を足すときは、**何を落とすかを同時に決める**
- 矛盾したら新しい方を残して古い方を消す。両論併記にしない

**例外は2つだけ。**①**原文・入力ログ**（追記のみ。既存を書き換えない）
②**棄却した仮説・採らなかった選択肢**（削除せず理由を残す。再発明を防ぐため）。
明示的に「過去を背景として残せ」と指示された場合を除き、この2つ以外で追記しない。

## 3. リンクは必須。関係型を付ける

`[[name]]` でメモリ同士を繋ぐ。**関係型は5本。増やさない。**

| 関係型 | 意味 | 双方向 |
|---|---|---|
| `根拠` | この記述を支える観測・原文 | 片方向可 |
| `反証` | この記述に反する記述 | **必須** |
| `置換` | この記述が古い記述を置き換えた | **必須** |
| `派生元` | 昇格・要約の元になった記述 | 片方向可 |
| `関連` | 上のどれでもない | 片方向可 |

記法は末尾に箇条書き。**`—` 以降の理由を省略しない。**

```markdown
## 関連
- 根拠:: [[観測ノート]] — 2月〜8月のエピソード5件
- 反証:: [[別の知見]] — 3か月更新が止まっている
```

- **理由を1行で書けないリンクは張らない。** 関係が分かっていないということ
- **`関連` に逃げない。** 他の4本が使えるなら必ずそちらを選ぶ
- **リンクゼロのメモリは孤立している。**要るかを疑う。それでも要るなら未存在の名前へ `関連` で張ってよい
- `反証` と `置換` を片方向にしない。**片側だけ読んだ AI が誤る**のはこの2つだけ
- リンク先を削除・改名したら、**張っていた側を同じ作業の中で直す**

適用範囲：**結論を持つノートのみ。** 原文・台帳・索引には関係型を付けない。

## 4. 入力側に構造を要求しない

**本人が書く場所にフォーマットを課さない。** 分解・分類・型付けは読む側（AI）で行う。
書く側に構造を求めると**器だけ残って中身が抜ける**形で壊れる。選択肢から型を選ばせる運用も同じ。
**型を付けるのは AI。**

## 5. 上限を持つ

**常時読み込まれる層には必ず上限を置く。** 膨張すると読まれなくなり、層ごと死ぬ。

- 上限値は**規約側が持つ。索引に現在値を書かない**（増減のたびに二重メンテになる）
- 超えたら**何を落とすかを同時に決める**。落とした候補と理由を作業ログか進捗に残す
- **上限は天井であって目標ではない。**埋めなくてよい

### 常時ロードされるファイルの実上限（Claude Code 公式）

| ファイル | 上限 | 超えたとき |
|---|---|---|
| `MEMORY.md`（索引） | **先頭200行 / 25KB で切り捨て**（ハード制限） | **超過分は黙って捨てられる。**140行以下へ書き直す |
| `CLAUDE.md` | 200行以内（推奨。トークンコスト） | `@path` import で分割するか `paths:` でスコープ |
| `~/.claude/rules/*.md` | **行数制限なし。**`paths:` の無いルールはセッション開始時にロード | 肥大したら `paths:` でスコープするか skill へ逃がす |

**ハード制限は索引だけ。**他はコストの問題だが、索引は警告なしに末尾が消える。
参照資料（点検表・手順書）を skill へ逃がしオンデマンドにするのが公式の推奨。

## 6. 索引の規約

- **1ファイル1行。本文を索引に書かない**
- フックは「**いつ開くか**」が判断できる粒度。要約・結論を書かない
  （結論を書くと、本体を直すたびに索引も直す二重メンテになる）
- **入力量に比例して行が増えるならフォルダ単位で1行にする。**
  比例して増える索引は索引ではなく複製
- **ファイルを新規作成・削除・改名したら、同じ作業の中で索引を直す**
- 索引が壊れていたら、手で直す前にまず自動修復を走らせる
- **行数は5節の実上限に従う。**索引は超過が無言で切り捨てられる唯一のファイル

## 7. 陳腐化させない

- **相対日付を残さない。**「先週」「今月」「最近」は絶対日付へ変換して書く
- **ファイル名・関数名・フラグ名・コマンド名を含むメモリは、それを根拠に推奨する前に実在を確認する**
- 誤りと分かったメモリは**削除する。**残して注記しない
- 保存前に同じ内容を扱う既存ファイルを探す。あれば**新規作成せずそれを更新する**
- **古い記述は、見つけたタイミングで削除して最新に置き換える。**
  そのために事前の畳む条件・検知器・カウンタを設けない

## 8. 新規メモリセットを作る前に

**「これを知らない AI と知っている AI で、返る答えが変わるか。」**
変わらないなら作らない。既存のどれかに1行足して終わらせる。

## 9. `~/.claude/projects/<project>/memory/` の書式

保管庫とは別に、Claude Code 自身が持つメモリ。**上の1〜8条はこちらにも適用する。**
以下はこの場所に固有の書式。

- **1ファイル1事実。** 派生できるもの（コード構造・git履歴・CLAUDE.md にある内容）は書かない
- その会話でしか効かないものは書かない

```markdown
---
name: <short-kebab-case-slug>   # ファイル名（拡張子なし）と一致させる
description: <1行。想起時の関連判定に使う>
metadata:
  type: user | feedback | project | reference
---

<事実。feedback / project は続けて **Why:** と **How to apply:** の行を書く>
```

| type | 内容 |
|---|---|
| `user` | 本人が何者か（役割・専門・好み） |
| `feedback` | 進め方への指示。訂正と確認済みのやり方の両方。**理由を必ず含める** |
| `project` | 進行中の作業・目標・制約で、コードや git 履歴から導けないもの |
| `reference` | 外部リソースへのポインタ（URL・ダッシュボード・チケット） |

索引は同ディレクトリの `MEMORY.md` に `- [Title](file.md) — フック` の形で1メモリ1行。
`[[name]]` の `name` は相手の `name:` スラッグ。

**2026-08-17 時点でこの場所のメモリファイルは0件。**書き始めるときにこの書式に従う。
なお**このファイル自身の分量・構成の基準はここにない** — `config-health-check` が
Claude Code 公式ドキュメントと突合して点検する。


## 10. 点検の自律実行

日次 `memory-health-check` が本規約への違反を点検し、**人の承認を待たずに是正する。**

**検査項目と、どこまで自律で直すかは
`C:\Users\nr202\projects\work\harness\scheduled-tasks\memory-health-check\reference\点検項目.md` が持つ。**
ここに写さない。基準の本体（本文1〜9条）はこのファイル、適用のしかたはあちら。

自律を成立させている条件は3つ。**どれか1つでも外れたら自律をやめる。**

1. **復元手順を1行で書けない修復は実行しない。** 表の分類よりこの条件が優先する
2. **サブエージェントのレビューが承認のゲートを兼ねる。** 人の承認を待たない
   （先例：[[20_抽出基準]] のL3昇格）。**レビューへは diff と該当条項だけを渡し、
   「なぜ直すか」を渡さない。**問いは「妥当か」ではなく「**失われる情報は何か**」
3. **削除・改名・統合は1周0件。** 追記は復元できるが削除はできない

**自律が壊れたときの差し戻し条件。**これは自律を止めるための安全弁であって、
メモリセットを畳むための検知器ではない。
**レビュー却下0のまま10周でレビュー不全／本人の事後取り消し1件で全件報告へ差し戻し。**

## 採らなかった選択肢（再検討しないため）

- **関係型を24型に増やす** — 選ぶコストが `関連` への逃げを生む。5本で足りない場面が3回出たら再検討
- **リンク用プラグイン**（Dataview / Breadcrumbs / Graph Link Types）— 読み手は AI でグラフビューではない
- **frontmatter プロパティでの関係表現** — 本文と二重管理になり、片方だけ更新される
- **全リンクの双方向化** — 片側だけ読んで誤るのは `反証` `置換` だけ。他は維持コストに見合わない
- **ストリームごとの索引** — 分散すると、どこを見れば全体が分かるかが失われる
- **点検項目を SKILL.md 本文に書く** — 二重管理。SKILL は駆動だけを持ち、基準は `reference/` が正
- **保管庫内（`<保管庫>\personal\rules\`）への配置** — 自動ロードされない
- **自律の線引きに「C表」を新設する** — 表を人が手で仕分けることになり、維持されない。
  「復元手順を書けない修復は実行しない」の1条件で自動的に振り分ける
- **安全弁を変更ファイル件数で切る**（案 N=10）— 索引1行と知見の統合が同じ1件に数えられる。
  **層 × 可逆性**で切り、削除行数に閾値を置く
- **規約・保管庫にモデル名を書く** — モデル可用性は harness 側で変わり、必ず陳腐化する（7節）。
  レビュアの指定は `CLAUDE.md` の1本に寄せる
