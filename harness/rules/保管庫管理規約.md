# 保管庫管理規約

**保管庫のどこに何を置き、どう書き込むか。**全プロジェクトへ自動ロードされる。
保管庫のルートは `C:\Users\nr202\iCloudDrive\iCloud~md~obsidian\`。以下 `<保管庫>` と書く。

> **他のルールとの分担** — `メモリ管理規約.md` はメモリの質の基準（4役・置換・リンク・上限・陳腐化・点検）を持つ。
> **このファイル**は置き場と書き込み方を持つ。ストリーム固有の手順は各ストリームの `AIメモリ/` が持つ。
> 記述が衝突したらこのファイルを正とし、**固有側を直す。**両論併記にしない。

## 1. ストリームの置き方

- `<保管庫>\personal\projects\<ストリーム>\` に、1案件1ストリームで並べる
- 停止したストリームは本人が `personal/projects/archive/` へ移す。archive 配下は、明示的な指示がない限り書き込まない
- ストリーム直下の構成は次のとおり。4役（索引・規約／設計・本体・作業ログ）の要件はメモリ管理規約1節が持つ

| 置き場 | 中身 | 書き手 |
|---|---|---|
| ストリーム直下の成果物 | 本体。読まれるもの | **人間からの明確な指示がない限り AI は編集しない** |
| `AIメモリ/` | このストリームの進め方（規約・設計）と作業ログ | AI |
| `作業履歴/` | 作業ごとの記録・情報収集・元データ（2節） | AI。本人が置いたファイルは書き換えない |
| `知見/` | 次回も使える手順・前提・落とし穴（2節） | AI |

**`作業履歴/` と `知見/` はストリーム直下にあっても本体ではない。**AI が書いてよい（メモリ管理規約1節の例外）。
本人も読む場所なので、置き場をストリーム直下にしている。

## 2. 作業履歴と知見

### 作業履歴

**1作業1フォルダ。**`作業履歴/<作業日>_<内容>/` に置く。日付の表記はそのストリームの既存のフォルダに合わせる。

- **作業の記録** — フォルダと同じ名前の `.md`。何をしたか、結果の数字、確かめたこと、戻し方、未決を書く
- **情報収集** — Web ページを読んで調べたら、ページのショートカット（`.url`）と要約（`収集内容.md`）を置く。要約には出典の URL を書き、原文を転載しない
- **元データ** — 本人が置いた PDF・CSV・メモは、そのまま残す。書き換えず、消さない。AI が作業用にコピーするときは scratchpad に置き、作業が終わったら消す
- 作業の中で状態が変わったら、その作業の記録を置換で更新する（メモリ管理規約2節）

### 知見

**次に同じ対象を扱う AI が、最初に読めば足りる内容。**作業履歴から、繰り返し使える部分だけを移す。

- 移す対象は、外部サービスの操作手順・データを読むときの前提・落とし穴・毎月の運用手順
- **移したら、作業履歴の側には要点とリンクだけを残す。**同じ手順を2か所に書かない
- 推論で書いたことには「未検証」と付ける。確かめたら外し、確かめた日付と方法を書く
- 知見と `AIメモリ/` の分け方：外部の対象（サービス・データ・手続き）の扱い方は `知見/`、このストリーム自体の進め方と作業ログは `AIメモリ/`
- 索引には `作業履歴/` と `知見/` をフォルダ単位で1行ずつ持つ（メモリ管理規約6節）

## 3. 保管庫への書き込み（iCloud）

**保管庫は作業中に外から書き換わる。**iCloud の実体化と並行セッションの書き込みが同時に走り、
同じファイルへ重ねて書くと `ファイル名 2.md` の衝突コピーができる。

- **書き込む直前に対象の mtime を見る。**直前に動いていたら書かない
- **書く前に読み直す。**別のセッションが同じファイルを書き換えていることがある。読み直した内容に追記された部分は消さない
- **同じファイルへ Edit を重ねない。**まとめて1回で書く。往復が増えるほど衝突の窓が広がる
- **書き込んだ直後に `〜 2.md` の有無を確認する。**あればその場で `fix-conflicts.sh` を回す
- **正本が消えて衝突コピーだけが残ったら、`fix-conflicts.sh` で戻す**（メモリ管理規約10節の但し書き）。
  手で改名しない。iCloud が移動と解釈して元へ戻す
- **索引は保管庫の中に置かない**（メモリ管理規約1節）。名前が変わると名前で参照している側から読めなくなる
