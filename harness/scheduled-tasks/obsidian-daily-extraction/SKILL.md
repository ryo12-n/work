Obsidian保管庫の日次抽出分類作業を実行してください。

保管庫のルートは `C:\Users\nr202\iCloudDrive\iCloud~md~obsidian\` です。

**この作業は自律的に完了させてください。**人の承認を待たずに、context への昇格まで実施します。
承認のゲートは fable のサブエージェントによるレビューが兼ねます。

## 0. まずルールを読む

作業を始める前に必ず以下を読んでください。この保管庫は独自のパイプライン設計を持っており、
読まずに進めると層の責務を壊します。

- `CLAUDE.md`
- `personal\AIメモリ\MEMORY.md` — **索引。全ファイルの実パスはここが持つ。**
  「常時」セクションと「保管庫を触るとき」セクションのファイルを開く

**このタスクが直書きするパスは、上の `MEMORY.md` の1本だけです。**
以下で `10_log/` `進捗.md` などと書いたものは、すべて索引が示す実パスに読み替えてください。

**保管庫は再編の途中で、実体はセッション中にも動きます**（2026-08-16 だけで
番号付き4層の移動とストリーム名の改名が2度あり、そのたびに索引の全リンクが切れた）。
パスを覚えず、毎回索引を引き直すこと。索引と実体がずれていたら、**索引を直してから作業する。**

## 1. 対象範囲

**前日分まで**を対象にします。日記は夜に書かれるため、17:00時点では当日分が存在しません。

入力ソースは3つ。前回の走査以降に増えた分だけを処理します。
走査済みの範囲は `進捗.md`（索引の「保管庫を触るとき」）の「外部ソースの走査状況」表にあります。

- `00_inbox/` — Obsidianに直接書かれた日記。**現在の日記の住処**
- **Craft**（MCPコネクタ `craft_read`）— 会話ネタ、ふとした分析・考察、はるかの取り組み、
  継続的な取り組み、飲食店・サービスの履歴分析など。
  `folders list` と `documents list --folder <folderId>` で新規ドキュメントを確認する
- **Notion**（MCPコネクタ）— 人間関係、はるか配下（好き嫌い等）、GTDタスク管理、出張履歴、家計など。
  `notion-list-recent-pages` で最近更新されたページを確認する

新規入力が1件もない日は、何もせずその旨を報告して終了してください。無理に成果を作らないこと。

## 2. 絶対に守ること

- **Craft と Notion には書き込まない。** Obsidian は抽出専用です。読み取りのみ
- **`00_inbox/` の既存の記述を書き換えない。** 原文です
- **元データ1件につき1ファイルを作らない。** 外部ソースの走査結果は
  `10_log/台帳_*.md` に1観測=1行で追記する。ファイル数を入力量に比例させない
- **台帳には表だけを置く。** 分析・評価・他ソースとの突合は `20_knowledge/` に書く。
  `10_log/` は再生成対象なので分析を書くと消えます
- **1観測は1行・1型。** 複数の台帳に二重登録しない
- **iCloud Drive の同期競合に注意。** 同一ファイルへの Edit を並列実行すると
  `ファイル名 2.md` という競合コピーが作られます。同一ファイルの編集は必ず直列で行うこと
- **iCloud は作業中にもファイルを同期します。** 長い作業では、書き込む直前に
  対象ファイルを読み直してください。古いコピーを上書きすると本人の編集が消えます

## 3. 手順

1. **着手前レビュー** — 何をどの層にどう書くかの計画を立て、Agent ツールを `model: "fable"` で
   呼び出してレビューを受けてから着手する（fable が使えない場合は `model: "opus"`）。
   観点は `00_パイプライン.md`（索引の「保管庫を触るとき」）の「レビュー観点」節にあります
2. **L0+L1** — 新規入力を意味単位に分解し、型を付けて該当する台帳に追記する。
   出典は Craft/Notion 由来ならドキュメント単位まで、`00_inbox` 由来なら行番号まで残す
3. **L2** — 採用基準は2つだけ。「次に同じ状況が来たとき行動が変わるか」と「反復回数」。
   反復回数は**エピソード単位**で数える（連日の同一エピソードへの言及は1回）。
   1回=仮説（`30_context/open.md`）、2〜3回=知見（`20_knowledge/`）
4. **既存知見の更新** — 新しい観測が既存ノートの反復回数を増やす場合、そのノートを更新する。
   反証が出た場合は削除せず「棄却」として理由を残す
5. **L3（context への昇格）** — 下の第4節に従って実施する
6. **完了後レビュー** — 変更したファイルをすべて渡して `model: "fable"` でレビューを受ける。
   **指摘が出たら修正し、修正後にもう一度レビューを受ける。**指摘が解消するまで繰り返す
   （最大3周。3周で解消しないものは未解決として報告に残す）
7. **`進捗.md` を更新** — 走査状況の表、次にやること、既知の課題、
   枠を争って見送った候補。このファイルは上書き更新。古い記述は削除して現在の事実だけを残す
8. **`personal\AIメモリ\MEMORY.md`（索引）を更新** — この作業でファイルを新規作成・削除・改名したなら、
   索引の行を同時に直す。`20_knowledge/` にノートを足したら1行足す。
   **日次log・`40_report/`・`projects/メンバー/` はフォルダ単位1行のままにする**（行を増やさない）

## 4. context への昇格（自律的に実施する）

`30_context/` は AI に常時渡される層です。上限があります。

| ファイル | 上限 |
|---|---|
| `self.md` | 5項目 |
| `判断ルール.md` | 30行 |
| `people.md` | 5名 |
| `open.md` | 10件 |

**昇格基準は「これを知らないAIと知っているAIで、返ってくる答えが変わるか」。**
接触頻度や重要そうに見えるかで選ばない。

自律的に昇格・削除して構いませんが、以下を守ってください。

- **上限を超えるなら、何を落とすかを同時に決める。** 落とした候補と理由を `進捗.md` に残す。
  残さないと次回また同じ比較をやり直します
- **既存項目を書き換える場合、その項目の証拠（反復回数・出典）が更新後も成立するか確認する**
- **判断に迷ったら昇格させない。** context は増やすより減らす方が難しい
- 昇格・削除の判断は完了後レビューの対象に必ず含めること。
  レビューで「昇格すべきでない」と指摘されたら差し戻す

`self.md` を書き換えた場合は、`進捗.md` に「効果検証の再実行が必要」と記録してください。
過去のA/B検証結果は旧 context に対するものになるためです。
