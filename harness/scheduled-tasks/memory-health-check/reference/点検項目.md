## 4. 安全弁 — 件数ではなく「層 × 可逆性」で切る

索引1行の追加と `20_knowledge/` の統合を同じ「1件」に数えない。

| 操作 | 1周の上限 |
|---|---|
| 索引・作業ログ・frontmatter への機械的修復（A表） | 上限なし |
| 結論を持つノート（`20_knowledge/` `30_context/` `AIメモリ/` のルール）への編集 | **3ファイル** |
| 削除・改名・統合 | **0件**（＝すべて報告） |

**累計削除行数が1周20行を超えたら、以降の修復を止めて残りを全件報告する。**
追記は復元できるが削除はできない。行数はその非対称性を直接測る。

上限に達した分は**滞留させず、次の周で先頭から再処理する**。

## 5. レビューの依頼方法

**追認機にしないための制約。守らないとレビューは意味を失う。**

- 依頼は `C:\Users\nr202\projects\work\harness\CLAUDE.md` の規定に従ってサブエージェントへ出す。**モデル名をここに書かない**
- **渡すのは「修復前後の unified diff」と「規約の該当条項」だけ。**
  親の「なぜ直すか」の説明を渡さない。渡すとレビューは修復の妥当性ではなく
  説明の内部整合を採点する機械になる
- **問いは「この修復は妥当か」ではなく「この修復で失われる情報は何か」。**
  前者は Yes バイアスが強い。後者は具体物を1つ挙げさせられるので空返事が検出できる
- 出力形式を固定する：**判定 / 失われる情報 / 復元手順**
- **レビューが復元手順を書けなかったものは実行しない**（0節）
- **却下された案と理由を実行ログに残す**（規約2節の例外②に該当し、上書き更新の原則に反しない）

## 6. 検知器 — 空洞化を検出する

規約8節が「空洞化の検知器を必ず1つ持つ」と要求している。
実行ログの固定行に**現在値のカウンタとして**持つ。**履歴ではないので A8 の対象外。**

| カウンタ | 発火条件 | 発火したら |
|---|---|---|
| 連続「異常なし」日数 | **14** | 毎日走らせる価値がない。**週次へ落とすことを報告で提案する** |
| レビュー却下件数 | **0 のまま10周** | レビューが機能していない。**B表を全件報告へ戻す** |
| 本人による事後取り消し件数 | **1** | 自律の判定が信用できない。**B表を全件報告へ戻す** |

**「異常なし」が続くほど人は報告を読まなくなり、実質無監査になる。**
この仕組みが最も壊れやすい経路なので、カウンタは毎回必ず更新する。

## 7. 報告の形

問題ゼロなら「**異常なし（N件点検）／連続M日**」の1行で終える。
問題があった場合のみ、以下を分けて箇条書きにする。

1. **直したもの**（A表 / B表を区別する）
2. **レビューが却下したもの**と理由
3. **報告のみのもの**（B4-B6, B8の一部, B9, B10、および安全弁で止まった分）
4. **カウンタの現在値**

ファイルは `パス:行` 形式。前置き・要約・励ましを書かない。
